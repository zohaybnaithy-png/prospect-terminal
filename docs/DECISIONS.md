# Decisions

Architecture and product decisions with their reasons. Newest last. A decision changes only by a new entry
that supersedes it. Proposals awaiting the owner are at the end. Details live in the linked docs.

| Id | Decision | Why | Where |
|---|---|---|---|
| D-001 | **Player is the central object**; orgs, teams, levels, games are context. Internal UUIDs; provider ids only in `source_identities`. | Survives promotions, trades, provider changes. | ARCHITECTURE.md, INGESTION.md |
| D-002 | **Statistics and Momentum are per level.** Never summed or normalized across levels without an approved method. | Level-of-competition adjustment is unsolved; blending misleads. | ANALYTICS.md, PRODUCT.md |
| D-003 | **Hosting: Vercel (Hobby) + build-time snapshot.** The Lightsail + Caddy + systemd target (deploy/) is a dormant alternative, kept but not run. | Zero ops, free tier, no runtime DB. | VERCEL.md, DEPLOYMENT.md |
| D-004 | **Snapshot-only runtime on Vercel.** `PT_DATA_SOURCE=snapshot`; the build exports a consistent READ ONLY snapshot and fails otherwise (`src/lib/vercel-build-guard.ts`). Runtime never opens a DB connection. | No DB credentials or connection limits at runtime; deterministic pages. | VERCEL.md §1, PR #22 |
| D-005 | **Precomputed per-level view models** are byte-verified at build and fall back to live computation on any mismatch (source fingerprint, V8 version, Math probes). | Cold start 4.4 s → ~1.1 s without risking wrong output. | VERCEL.md, `src/services/competition/views-store.ts` |
| D-006 | **Prefetch off by default** (`@/components/ui/app-link`); router cache `staleTimes.dynamic=300`. | 50–65 prefetches per page view would exhaust Hobby invocation limits. | VERCEL.md §2 |
| D-007 | **No `loading.tsx`.** | Streaming fixes the status at 200 and turns unknown-player 404s into soft 404s. | VERCEL.md §2 |
| D-008 | **CDN caches plain page requests only** (`Vercel-CDN-Cache-Control: max-age=300, swr=86400`); RSC/router requests and `/health` are never cached. | Vercel minimal mode would let a forged RSC request poison a shared key. | VERCEL.md §3 |
| D-009 | **CSP allows `'unsafe-inline'`** for scripts/styles. | Next.js inline payload and Recharts; acceptable with no accounts or user content. Revisit before accounts. | PRODUCTION-READINESS.md L5 |
| D-010 | **Momentum V1 Balanced is the only shipped model.** Grade, P(MLB), Similarity, Breakout, Prospect Priority, Pure Performance need owner-approved methodology. | Formulas must be defensible before users rely on them. | ANALYTICS.md, CLAUDE.md |
| D-011 | **Ingestion guarantees are never weakened for performance**; one transaction per apply; bulk writer (~30 round trips). | Data integrity and replay safety. | CLAUDE.md, INGESTION.md |
| D-012 | **MLB Stats API is development-only** until licensing is resolved; no scraping of proprietary sites; no bulk export. | Terms: individual, non-commercial, non-bulk. | DATA-LICENSING.md |
| D-013 | **Agent workflow:** agents branch from `staging`, open PRs, watch CI, run `verify:preview`; merges, Production, settings, secrets and ingestion need the owner. Project settings deny merge/Production commands. | Autonomy with hard safety boundaries. | AUTONOMOUS-WORKFLOW.md |
| D-014 | **Deployment Protection stays on for all deployments**; agents use one Protection Bypass for Automation secret, header-only, scoped to the deployment's own host. | Private previews without disabling protection. | AUTONOMOUS-WORKFLOW.md §3 |
| D-015 | **The Momentum golden test is bit-exact and Linux is the canonical platform.** It fails on macOS arm64 (1 of 2638 outputs, `Math.tanh` last bit). Never regenerate or loosen it; verify on CI. | Exactness catches real regressions; libm differences are not regressions. | TASKS.md T-305 |
| D-016 | **Staging merges are human until the owner approves the guarded path** (`npm run gate:staging` is check-only). Sensitive paths (CI, agent rules, config, schema, ingestion writes, gates, lockfile) always need a human. | Least privilege; the gate is reviewed before it gains merge power. | `scripts/staging-gate-support.ts` |
| D-017 | **Per-visitor state never reaches the server render.** The watchlist lives only in the browser's localStorage (guarded, re-validated); `/watchlist?ids=` is rendered from the URL alone, and star buttons render a neutral state on the server, so CDN-cached HTML is identical for everyone. No cookies, no accounts, no tracking. | Snapshot-only, CDN-cached site; privacy. | `src/lib/watchlist-storage.ts`, T-202 |
| D-018 | **T-301 re-scoped (owner, 2026-11-26):** no per-snapshot `playerLevels` index (≈0.5 ms per profile, extra memory); instead `playerProfile` builds only the profiled player's season row. | Measured cost is in `playerProfile` (~10 ms), not `playerLevels`. | TASKS.md T-301 |
| D-019 | **Per-instance rate limiter accepted on Vercel as documented (owner, 2026-11-26).** T-303 check 7 stayed inconclusive (requests spread over instances, no 429); no diagnostic route added. Revisit before public launch. | Site is behind Deployment Protection; a debug route adds surface for little gain now. | VERCEL.md, TASKS.md T-303 |
| D-020 | **Age relative to level (owner-approved 2026-11-26, T-401):** a player's decimal age minus the median decimal age of all players with a completed-game line at that level this season and a known birth date, both on the level's as-of date; rounded to 0.1 years; positive = older. Not shown below 20 qualifying players. One median per level (not per role); never combined across levels. | Simple, transparent context from the snapshot alone; no model. | `src/services/players/level-age.ts` |
| D-021 | **Breakout detection method approved as proposed (owner, 2026-11-26, T-402):** docs/BREAKOUT-METHOD.md as written, including q = 0.10, the 70th-percentile level standing, persistence 2 of 3, upward only, age display-only, the validation plan and the §7 success criteria. Next deliverable is the offline validation script and report only; no user-facing feature until a level passes §7. | Defensible, falsifiable method before anything is shown. | docs/BREAKOUT-METHOD.md |
| D-022 | **Breakout validation runs as approved (owner, 2026-11-27, T-405),** decided after the synthetic findings (BREAKOUT-METHOD.md §10) and before any real-data run: statistic shrunk-over-raw-se, blocks 100/100, all D-021 values. No revision is chosen after seeing real results. | Avoids tuning to the data. | docs/BREAKOUT-METHOD.md §10 |
| D-023 | **Breakout detection is not available at any level (validation result, 2026-11-27, T-405).** Run as approved on the 2026 snapshot (8b418063511b): 0 flags at every cutoff for all 4 levels × 2 roles; every level fails §7 (criteria 2–5). False-positive control worked (0.009–0.022 null flags per date). The feature is not built. Any revision is a new proposal with its own validation, not a re-run with loosened values. | Pre-registered criteria decide; results are not tuned. | docs/reports/breakout-validation-2026.md |
| D-024 | **Player similarity method (owner-approved as proposed 2026-11-27, T-404):** same level, role and season; profiles of shrunk rates (hitters K%, BB%, ISO, BABIP, SB rate; pitchers K%, BB%, HR/BF, BABIP, BF/app) plus age vs level (D-020); per-level shrinkage from split-half reliability; reliability-weighted Euclidean distance on z-scores with equal base weights; score 100·exp(−D²/2); top 5. Validation (§6) with a synthetic check first; success criteria §7, including the "browsing aid only" outcome when the holdout test fails. Shown nowhere until validated and approved for display. | Descriptive, explainable per dimension; no outcome data to fit weights against. | docs/SIMILARITY-METHOD.md, `src/analytics/similarity/` |
| D-025 | **Similarity validation result (2026-11-27, T-406):** pre-registered criteria on the 2026 snapshot. Stability passes everywhere; the holdout test fails at 6 of 8 level × role (gains ≈ 1% where it passes); face validity fails for hitters at every level (position-blind) and passes for pitchers. Pitchers: browsing aid only, no predictive claim. Hitters: not available until an owner-approved position rule is re-validated. Nothing is shown until the owner approves the display (separate task). | Criteria fixed before the run; no tuning after results. | SIMILARITY-METHOD.md §11, docs/reports/similarity-validation-2026.md |
| D-026 | **Hitter position-group rule (owner-approved 2026-11-27, T-407):** a hitter's similar players come only from qualified hitters of the same position group by primary position: C; IF (1B, 2B, 3B, SS); OF (LF, CF, RF); otherwise the position itself (e.g. DH). A group with fewer than 20 qualified hitters at the level gets no lists ("not enough similar players"). Profiles, weights and scores unchanged; pitchers unchanged. Validation re-run with the D-024 criteria; chance and the single-stat baseline are computed within the group. | The D-025 face-validity review found hitter lists position-blind (catchers with first basemen and shortstops). | SIMILARITY-METHOD.md §12 |
| D-027 | **Similarity re-validation with the position rule (2026-11-27, T-407):** hitters pass stability, face validity and population at every level; holdout passes at Double-A and Single-A with gains of about 1% (no predictive claim). With D-025 for pitchers: every level × role qualifies as a browsing aid only ("similar so far this season"). Not shown until the owner approves the display. | Criteria fixed before the run (§12 committed first). | SIMILARITY-METHOD.md §12, docs/reports/similarity-validation-2026.md |
| D-028 | **Similar players shown on profiles (owner-approved 2026-11-27, T-408):** "Similar at <level> so far this season", a browsing aid with no predictive claim. Score floor 70 (owner choice): lower neighbors are not listed; none at or above it → "no close match at this level". Each neighbor shows position, Bats/Throws, sample (flagged at a 3× difference), observed rates and closest/furthest dimensions (furthest ranked by weighted contribution w·Δz²; closest only among dimensions weighted ≥ 0.3). Not offered for the AFL. Method explained on `/data#similarity`. | Display rules from the two face-validity reviews (SIMILARITY-METHOD.md §11–§12). | `src/services/players/similar.ts`, `src/components/player/similar-players.tsx` |
| D-029 | **Prospect Grade method approved as proposed (owner, 2026-11-28, T-403):** statistical Grade = expected MLB value over six seasons (20–80, tiers from historical outcomes) from a two-stage regularized regression (P(MLB) × value given MLB); forward-in-time validation on 2012–2019 cohorts against a level + age + OPS / K−BB% baseline, criteria GRADE-METHOD.md §7 incl. "P(MLB) only" and "no Grade". Order: sizing estimate → owner approves historical ingestion (T-501) → validation → display; nothing public before T-601. Draft round as an input still open. | A Grade is a prediction; only past cohorts can validate it. | docs/GRADE-METHOD.md |
| D-030 | **Historical data as season totals (owner, 2026-11-28, T-501):** MiLB 2012–2019 and 2021 (the four full-season levels) and MLB 2013–2026 are loaded as player season totals per level (one new normalized record type and table) instead of per-game box scores. Build the code first (PRs only); then the completeness check against box scores, a read-only preview, and an apply only with explicit approval. Draft round as a Grade input still open. | ≈ 100k rows, stays on Neon Free; the Grade needs season-level inputs only. | docs/HISTORICAL-INGESTION-SIZING.md |
